# Evaluation workflows: offline, in CI, and continuous in production

**Status: one offline path built.** Feature 007 evaluates one response at a time
with the local `azure-ai-evaluation` SDK and stores the verdict as a span
(`evaluate_call.py`), then reads it back from a separate process
(`query_evaluations.py`). Cloud evaluation runs, the CI evaluation action,
continuous evaluation and scheduled evaluation are documented here and have not
been built.

Every behavioural claim comes from the Microsoft Learn pages under *Sources*,
read on **2026-09-25**. Exam objectives: *Set up automated evaluation workflows
by using built-in and custom evaluation metrics* and *Examine continuous
monitoring in Foundry*.

---

## 1. Three stages, three questions

Learn places evaluation at three points of the application lifecycle:

| Stage | Question | Tools |
| --- | --- | --- |
| **Base model selection** | which model fits this task, safely? | Foundry benchmarks (public or own data), evaluation SDK against a model endpoint |
| **Pre-production** | is this app or agent ready to ship? | evaluation on your own dataset (quality, safety, custom evaluators), **AI Red Teaming Agent** |
| **Post-production** | is it still good on real traffic? | operational metrics, **continuous evaluation**, **scheduled evaluation**, **scheduled red teaming**, Azure Monitor alerts |

The post-production list, verbatim:

> - «**Continuous evaluation**: Quality and safety evaluation of production
>   traffic **at a sampled rate**»
> - «**Scheduled evaluation**: Scheduled quality and safety evaluation using
>   **test datasets** to detect system **drift**»
> - «**Scheduled red teaming**: Scheduled adversarial testing to probe for
>   safety and security vulnerabilities»
> - «**Azure Monitor alerts**: Notifications when outputs fail quality
>   thresholds or produce harmful content»

The difference between the first two is the data: continuous evaluation scores
**live traffic**; scheduled evaluation scores a **fixed dataset** on a timer, so
a change in score is a change in the system.

## 2. Offline and online

- **Offline evaluation**: a fixed dataset, before release. Repeatable, and the
  only place a ground truth is usually available.
- **Online evaluation**: production traffic, after release. Live traffic
  carries no reference answer, so evaluators that require `ground_truth`
  (textual similarity, Response Completeness, Document Retrieval) cannot run
  on it.

Learn's GitHub Action page uses the word directly: it «enables **offline
evaluation** of Microsoft Foundry Agents within your CI/CD pipelines».

---

## 3. Offline, two SDK paths

| | Local evaluation | Cloud evaluation |
| --- | --- | --- |
| Package | `azure-ai-evaluation`, `evaluate()` | `azure-ai-projects` ≥ 2.x, OpenAI-compatible `evals` API |
| Portal | **Foundry (classic)** only | new Foundry |
| Where evaluators run | your machine; judge calls go to your deployment | Foundry service; «without managing local compute» |
| Data | JSONL only | JSONL or CSV, datasets, model or agent targets, stored traces, conversations, synthetic data |
| Mapping syntax | `${data.x}`, `${outputs.x}` | `{{item.x}}`, `{{sample.output_text}}` |
| Results | returned dict; optionally logged to the project with `azure_ai_project` | stored in the Foundry project; retrievable by SDK, portal, or routed to App Insights |
| Role | project access for logging | **Foundry User** on the project |

A cloud evaluation run has three steps: define the data shape and the
evaluators (testing criteria), create the evaluation, start a run and poll it.

### Where the evaluated responses come from

Cloud evaluation offers seven starting points. The ones to recognise:

- a dataset that already has query **and** response
- queries only, with a **model or agent target** that generates the responses
  during the run
- **stored responses or traces** from a deployed model or agent
- **synthetic** queries generated by the service
- **simulated conversations** for multi-turn agents

The local SDK's equivalent of a target is the `target=` parameter: any Python
callable, whose outputs are mapped with `${outputs.x}`.

### Service limits

- 2 MB per row, 100,000 rows per batch evaluation
- evaluation run creation is rate-limited at tenant, subscription and project
  level; a refusal carries a `retry-after` header, and Learn prescribes
  exponential backoff
- batch evaluation runs only in listed regions (North Europe and Sweden Central
  are both listed)

## 4. In CI: the evaluation GitHub Action

`microsoft/ai-agent-evals` runs an offline evaluation of **Foundry agents**
inside a workflow.

- Inputs: project endpoint, a judge `deployment-name`, `agent-ids` in the form
  `name:version`, a `data-path` JSON file with the evaluator list and the
  queries. Optional `baseline-agent-id`.
- Authentication: Entra ID through `azure/login` with **OIDC** federated
  credentials; the workflow needs `id-token: write`.
- Output: the job summary shows each metric with **confidence intervals**, and,
  for several agents, a **pairwise statistical significance test** against the
  baseline.

> «To minimize costs, **don't run evaluation on every commit**.»

The significance test is the point of the action: a score that moved by less
than its confidence interval did not move.

## 5. Online: continuous evaluation

Continuous evaluation is an **evaluation rule** attached to agent traffic.

```python
EvaluationRule(
    action=ContinuousEvaluationRuleAction(eval_id=eval_object.id, max_hourly_runs=100),
    event_type=EvaluationRuleEventType.RESPONSE_COMPLETED,
    filter=EvaluationRuleFilter(agent_name=agent.name),
    enabled=True,
)
```

- **Trigger**: each completed agent response (`RESPONSE_COMPLETED`).
- **Cap**: `max_hourly_runs`. **The default limit is 100 runs per hour.**
  When it is reached, further runs are **skipped** until the next hour.
- **Sampling** in the portal wizard: **Random** or **Intelligent sampling**,
  plus a maximum number of traces.
- **Permission**: the **project's managed identity** needs **Foundry User**.
  Without it the rule exists and no results appear.
- **Evaluators**: built-in and custom evaluators both work.

**Scheduled evaluation** uses a `Schedule` with a `RecurrenceTrigger` (for
example daily at 09:00) and an `azure_ai_trace_data_source_preview` data source
filtered by agent and time window, or a golden dataset.

Results appear on the agent's **Monitor** tab (`genai-production-monitoring.md`
§ 1) and in **Evaluations → Recurring Configs**.

### Cost

> «Evaluations in the agents playground are **enabled by default** for all
> Foundry projects and are included in consumption-based billing.»

Turning them off means deselecting every evaluator in the playground's metrics
panel. Risk and safety evaluations and playground evaluations bill under
Foundry Observability pricing; LLM-judge evaluators also bill the judge's
tokens.

## 6. What this repository measured, and what it did not

**Built:** one offline, per-call evaluation, local SDK, results written as
custom spans and read back by a second process. This design proved one thing
Learn does not state: **a record is verified when a separate process reads it
back**, and until F6 was fixed the read-back failed while every write reported
success.

**Found, not fixed (F9):** a judge call that fails still exports a span with no
score, and the readers count it as an evaluation. Learn's cloud-evaluation
contract handles the same case explicitly: a custom evaluator that raises is
recorded as `0.0` and **marked as an error**; an endpoint evaluator returns
`status: "error"` with `passed: null`. The repository's span has no status
projection yet.

**Not built:** cloud evaluation runs, dataset or target data sources, the
GitHub Action, continuous evaluation rules, schedules, scheduled red teaming,
cluster analysis of failures.

**Where this repository diverges from Learn:** results live in Application
Insights as custom spans, queried with KQL. Learn's cloud evaluation stores
results in the Foundry project, with a `report_url` per run, and routes them to
Application Insights only when connected.

## 7. What this note would cost to verify

A cloud evaluation run of ten rows with two LLM-judge evaluators costs the
judge's tokens, cents. Continuous evaluation needs an **agent** with traffic;
this repository has none, and generating traffic to feed it is the cost. The
cheap bound is `max_hourly_runs`: set it to a single-digit value and the spend
per hour is capped by construction. The GitHub Action reuses the existing OIDC
identity, but that identity's custom role would need the evaluation data
actions added, per `infra/DEPLOY.md` § 5.

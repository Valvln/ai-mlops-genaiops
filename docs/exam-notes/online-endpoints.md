# Managed online endpoints — documented, not measured

**Status: no online endpoint has ever been created by this repository.**
Feature 005 deliberately built a batch endpoint instead, and said so in
`mlops/training-pipeline/batch-endpoint.yml`: *"The exam objective covers both;
the wallet does not."* Everything below therefore comes from the Microsoft Learn
pages under *Sources*, read on 2026-08-18 — except the billing section, which
points at figures this project measured and does not restate them.

---

## 1. Endpoint and deployment are two objects

This is the single most load-bearing distinction in the whole topic, and this
project has now got it wrong twice in simulations.

| Object | Holds | Billed |
| --- | --- | --- |
| **Endpoint** | a name unique in the region, an HTTPS scoring URI, an auth mode, a traffic rule | **nothing** |
| **Deployment** | the model, the environment, the scoring code, `instance_type`, `instance_count` | **the VMs, continuously** |

One endpoint can hold several deployments. The routing rule on the endpoint
decides which one serves a request, which is what makes blue/green possible at
all — a single object with no separation between address and implementation
cannot do a staged rollout.

**Costs are in `compute-cost-model.md` § 4.3 and § 4.5 and are not repeated
here.** The one sentence worth carrying across: `instance_count` is a
*reservation, not a reaction to load*, there is no scale-to-zero, and a failed
deployment that got as far as creating compute still bills.

## 2. What a deployment needs

| Attribute | Note |
| --- | --- |
| `model` | a registered `azureml:<name>:<version>`, or an inline path |
| `code_configuration.code` | directory of scoring source |
| `code_configuration.scoring_script` | must define `init()` and `run()` |
| `environment` | registered environment, or inline image + conda file |
| `instance_type` | VM size, from the managed-online-endpoint SKU list |
| `instance_count` | "For high availability, set the value to at least `3`" |

**Quota is reserved at 120%**: `ceil(1.2 × instances) × cores` must be available.
Ten `Standard_DS3_v2` (4 cores) needs quota for 48 cores, not 40. The reserve is
for system-initiated upgrades and recovery, and "won't incur cost unless such
operations run". Some SKUs are exempt; the SKU list names them.

### The scoring script

> "This Python code must have an `init()` function and a `run()` function. The
> `init()` function is called after the model is created or updated, for example
> to cache the model in memory. The `run()` function is called at every
> invocation of the endpoint to do the actual scoring and prediction."

**`init()` once per worker, `run()` once per request.** That asymmetry is the
whole design: anything expensive — deserialising a model, opening a client —
belongs in `init()`, or it is paid on every request.

`mlops/training-pipeline/scoring.py` is a working example of the same contract
on the batch side, where `run(mini_batch)` receives a **list of file paths**
rather than an HTTP payload and returns a DataFrame. The function names and the
call frequency are shared; the argument and the return type are not.

### Deployment flavours

| | No-code | Low-code | BYOC |
| --- | --- | --- | --- |
| Scoring script | autogenerated | yours | inside the image |
| Environment | curated, implicit | curated or custom | inside the image |
| Requires | MLflow or Triton model | a scoring script | a container |

A caution this repository paid for: **an MLflow model does not guarantee that
no-code deployment is available.** On the batch path it was defeated by a
dependency conflict in the environment Azure ML synthesises from the model's
`conda.yaml` — `scoring.py`'s docstring carries the evidence. The feature is
real; its availability is a property of the runtime stack, not of the model
format.

## 3. Authentication

`auth_mode` is set on the **endpoint**, not on the deployment.

| `auth_mode` | Lifetime | Endpoint types | RBAC needed to score |
| --- | --- | --- | --- |
| `key` | never expires; rotate with `regenerateKeys` | managed and Kubernetes | no |
| `aml_token` | short-lived, carries `refreshAfterTimeUtc` | managed and Kubernetes | no |
| `aad_token` | per Entra policy, typically 60–90 min | **managed only** | yes — `score/action` |

The exam-shaped facts:

- **`aad_token` is managed-only.** On a Kubernetes online endpoint it is
  rejected; use `key` or `aml_token`.
- **Keys and tokens are fetched by a control-plane operation and used for a
  data-plane one.** Retrieving them needs
  `onlineEndpoints/listKeys/action` or `onlineEndpoints/token/action`; *using*
  them to score needs `onlineEndpoints/score/action`. Both are in the built-in
  **AzureML Data Scientist** role.
- **The audience differs by plane**: `management.azure.com` for control plane,
  **`ml.azure.com`** for data plane. A token with the wrong audience is a 401,
  not a 403.
- 403 means the identity lacks `score/action`. 401 means the token is missing,
  expired, or for the wrong audience.

This is the same data-plane / control-plane split that cost this project a
Domain 1 question on Key Vault. It is the same shape on a third service.

## 4. Traffic, mirroring, rollout, rollback

### Live traffic

Percentages across deployments must total 100. Traffic is set on the endpoint,
and only after the deployments exist:

```bash
az ml online-endpoint update --name $ENDPOINT_NAME --traffic "blue=90 green=10"
```

A request can bypass the rule entirely with a header — this is how you smoke-test
a deployment that has 0% of traffic:

```
azureml-model-deployment: green
```

### Mirrored traffic

```bash
az ml online-endpoint update --name $ENDPOINT_NAME --mirror-traffic "green=10"
```

Mirroring copies a percentage of live traffic to a second deployment and
**discards its responses**; clients keep receiving the live deployment's answers,
while the shadow deployment's metrics and logs are recorded. The documented
limits:

- **Maximum 50%** mirrored, to protect the endpoint's 5 MBps bandwidth quota.
- **Only one deployment** in an endpoint can receive mirrored traffic.
- A deployment receives **either** live traffic **or** mirrored traffic, never
  both.
- Mirroring is **not supported on Kubernetes online endpoints**.
- If a request names a deployment with the `azureml-model-deployment` header, it
  is **not** mirrored. Only unrouted traffic is.

Disable by setting it to zero, not by deleting anything:
`--mirror-traffic "green=0"`.

### The rollout sequence

1. Create `green` alongside `blue` with **0% traffic**.
2. Test it directly with the `azureml-model-deployment` header.
3. Optionally mirror ≤50% and watch latency and error rates.
4. Shift a real slice: `--traffic "blue=90 green=10"`.
5. Complete: `--traffic "blue=0 green=100"`.
6. Delete `blue` — **and only then does it stop billing.**

### The rollback

**Move the traffic, do not delete anything.** `--traffic "blue=100 green=0"` is
one control-plane call against a deployment that is already warm. Deleting
`green` also stops the errors but takes longer, destroys the logs that explain
the failure, and requires a full redeploy to try again. Deleting the endpoint
would additionally change the scoring URI that clients hold.

The ordering is the exam answer: **fastest rollback is a traffic change; the
cost stops only at deletion.** Those are two different operations answering two
different questions, and the simulation asked the first one.

## 5. Autoscale

Managed endpoints autoscale through **Azure Monitor autoscale** — metric rules
(CPU > 70%), schedule rules, or both. It moves `instance_count` between a
minimum and a maximum, and **the minimum is at least 1**. Autoscale is a
throughput mechanism, not a cost-to-zero mechanism.

## 6. Debugging, in increasing order of cost

1. **Azure ML inference HTTP server** — a Python package, no Docker, no Azure.
   Wraps the scoring script as an HTTP endpoint locally.
2. **Local endpoint** — needs Docker Engine. Limits worth knowing: no traffic
   rules, no authentication, no probes, **one deployment per endpoint**, local
   files and local conda only.
3. **Container logs in Azure** — the inference server console log carries the
   scoring script's `print`/`logging` output; the storage initializer log says
   whether the model and code downloaded at all.

The first two cost nothing and are where a scoring script should fail. Feature
005 learned the equivalent lesson from the other direction: a wrong assumption
inside `init()` fails "at serving time, which is the most expensive place to find
out".

## 7. What this note would cost to verify

A managed online deployment on `Standard_DS1_v2` bills **≈0.06 €/hour from
creation to deletion**, traffic or no traffic (`compute-cost-model.md` § 4.3).
A two-hour exercise that creates, invokes, rolls out, rolls back and deletes
costs **≈0.12 €** — plus a custom environment's image build, which § 7.5 measured
at ≈0.28 €/hour of build time on a machine the customer does not choose, plus the
container registry at 0.1462 €/day for as long as the environment exists.

So the exercise is cheap and **the forgetting is not**: an endpoint left up for a
month is ≈42 €. Any future feature that creates one must delete the deployment in
the same session, and `infra/DEPLOY.md` § 6 is where that belongs.

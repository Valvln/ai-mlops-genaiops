# Data model — Block 5

**Date**: 2026-08-27. Entities from [spec.md](./spec.md) § Key Entities, resolved
into concrete shapes. Decisions behind them are in [research.md](./research.md).

Six entities. Two of them live in Azure (the index and its documents); four are
files in the repository. The split matters: **everything that cannot be
regenerated by a command is version-controlled**, and the one thing in that
category is the label set.

---

## 1. Corpus

The repository's own `docs/exam-notes/*.md`, read from the working tree.

| Property | Value |
| --- | --- |
| Source | `docs/exam-notes/*.md`, 18 notes |
| Size | ~284 KB, ~41.600 words |
| Token count | **measured, not estimated** — `tiktoken`, `o200k_base`, before chunking (FR-002) |
| Provenance | the git commit the corpus was read at, recorded on every run |

No copy is made. The corpus is the tree at a commit, and the commit is what makes
a run reproducible.

⚠️ **The corpus is self-referential**: notes about Azure AI Search, indexed into
Azure AI Search, queried with questions about Azure AI Search. This is the case
study the author asked for, not an accident. Its limits belong in the write-up
(FR-023), not in a footnote.

## 2. Chunk

One retrievable unit. Produced locally, embedded locally, pushed to the index.

| Field | Type | Notes |
| --- | --- | --- |
| `chunk_id` | string, key | `<note-slug>--<nnn>`, URL-safe. The index key must be a valid document key |
| `note` | string, filterable, facetable | source filename, e.g. `rag-chunking-strategies.md` |
| `heading` | string, searchable | the nearest enclosing H2, carried into the semantic configuration as the title field |
| `content` | string, searchable | the chunk text |
| `content_vector` | `Collection(Edm.Single)` | 3072 dimensions, `text-embedding-3-large` |
| `token_count` | int32, filterable | measured, kept so the distribution can be reported |
| `corpus_commit` | string, filterable | the commit the chunk was cut from |

**Chunking rule**: split each note on H2 boundaries first, then window any section
longer than the cap. **512 tokens, 128 overlap.**

⚠️ The 512/25 % pair is the *first* of the two mutually inconsistent
recommendations Learn publishes on the same page — the other is 200 words with
10–15 % overlap (`rag-chunking-strategies.md` § 2). One of them was chosen and
the choice is recorded; the inconsistency is not resolved by this feature, and
the chunk-size sweep that could have resolved it is out of scope by decision.

**Estimate**: ~55.000 tokens at an effective stride of 384 → **≈145 chunks**.
Vector footprint 145 × 3072 × 4 B ≈ **1,8 MB**, against a 50 MB service limit.
The estimate is a prediction; SC-006 replaces it with the measurement.

**Documents are never deleted to make room.** If the quota binds, that is US2's
finding, not an obstacle to route around.

## 3. Index

One index, in one free search service. Data-plane object — created by script, not
by Bicep, because indexes are not ARM resources.

| Element | Value |
| --- | --- |
| Fields | as § 2 |
| Vector profile | HNSW, cosine, default parameters |
| Vector dimensions | 3072 |
| Semantic configuration | one, titled `default`: title = `heading`, content = `content` |
| Analyzer | default (`standard.lucene`) for `content` |

**One index serves all four retrieval methods.** They differ only in the query
(FR-007), which is the property that makes the comparison a comparison and keeps
the embedding cost paid once (FR-005 scenario 5).

Compression and quantization are **not** configured: measuring them is out of
scope, and adding an unmeasured lever would change the vector size SC-006 reports.

## 4. Question set

The longest-lived artifact this feature produces, and the only one no command can
regenerate. Version-controlled at
`rag-optimization/rag-block5/questions/questions.jsonl`.

```jsonl
{"question_id": "q01", "query": "...", "note": "the note the author expects", "kind": "answerable"}
```

| Field | Notes |
| --- | --- |
| `question_id` | stable; labels join on it |
| `query` | the query text, as it would be typed |
| `note` | what the author *expects* to be relevant, before any retrieval. Not a label — a record of the prior, kept so a surprise is legible as a surprise |
| `kind` | `answerable` or `control` |

**~20 questions**, sized to be labelled in one sitting.

**At least one `control`** — a question whose answer is genuinely absent from the
corpus. Its labels are all `0`. It is kept, never deleted: a method that "finds"
something for it is exhibiting a defect, and that is worth catching (spec, Edge
Cases).

## 5. Retrieval run

One question set executed under one retrieval method. Written to
`rag-optimization/rag-block5/runs/<method>.jsonl`, **not** committed — regenerable
from the index by command.

```jsonl
{"question_id": "q01", "method": "hybrid_semantic", "corpus_commit": "abd8e9e",
 "retrieved": [{"chunk_id": "...", "rank": 1, "score": 3.41, "score_field": "@search.rerankerScore"}]}
```

| Field | Notes |
| --- | --- |
| `method` | `keyword` \| `vector` \| `hybrid` \| `hybrid_semantic` |
| `retrieved` | top **10**, in the order the service returned them |
| `score` | the number that **determined this ordering** |
| `score_field` | ⚠️ which property it came from — see below |

⚠️ **Three score ranges live under two property names.** BM25, pure vector
similarity and RRF all arrive as `@search.score`, on three incompatible scales;
semantic reranking arrives as `@search.rerankerScore`, 0–4
(`rag-hybrid-search-and-ranking.md` § 4). Recording `score_field` alongside the
value is what stops a later reader from putting four columns of unrelated numbers
side by side and drawing a line through them.

**Scores are never compared across methods.** Only the metrics in § 6 are.

The four runs share one embedded corpus and one embedding per query. Changing the
method costs nothing; changing the chunking would cost the whole corpus again,
which is why the sweep is out of scope.

## 6. Label set (qrels) and comparison

### Labels

`rag-optimization/rag-block5/questions/labels.jsonl` — **version-controlled**.

```jsonl
{"question_id": "q01", "chunk_id": "rag-chunking-strategies--003", "query_relevance_label": 3}
```

| Label | Meaning |
| --- | --- |
| `0` | not relevant |
| `1` | marginally relevant — mentions the subject |
| `2` | relevant — partially answers |
| `3` | fully relevant — answers the question |

Declared to the evaluator as `ground_truth_label_min=0`,
`ground_truth_label_max=3`, **explicitly**, because the SDK defaults are `0` and
`4` while Learn's own example passes `1` and `5` ([research.md § R8](./research.md)).
`fidelity` weights labels over `range(min + 1, max + 1)`, so a range declared one
point off reweights the metric silently instead of raising.

**Built by pooling** ([research.md § R9](./research.md)): the union of chunks
returned by all four methods is what gets labelled. Retrieval therefore runs
before labelling.

### Comparison

`rag-optimization/rag-block5/results/comparison.md` — committed, it is the
deliverable.

| Method | ndcg@3 | fidelity | xdcg@3 | top1_relevance | holes_ratio |
| --- | ---: | ---: | ---: | ---: | ---: |

`ndcg@3` is the ranking-shaped metric and `fidelity` the recall-shaped one
(FR-011). `holes_ratio` is reported for every run and gates the whole table
(FR-012): if it is high, the comparison is declared unreliable rather than
published.

The `*_passed` labels the evaluator emits against its seven built-in thresholds
are recorded beside the scores and **not** used to decide anything. Block 4's F5
is the reason.

## 7. Finding

A recorded divergence between a source and a measurement, in
`specs/008-rag-retrieval-quality/findings.md`, following block 4's format.

| Field | Notes |
| --- | --- |
| Severity | what it costs |
| The command | what was run |
| The output | verbatim, including the error text |
| Which is wrong | the source or the measurement, and on what evidence |

Each of the six research notes ends this feature with either a **verification**
beside a claim it confirmed or a **finding** recording one it contradicted
(FR-024, SC-012). Two are already spoken for at plan time: the regional gate on
free-tier semantic ranking (§ R2) and the model-availability-versus-quota gap on
`text-embedding-3-large` (§ R3).
